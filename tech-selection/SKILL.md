# 技术选型

目标：**直接做选择，不做技术百科。**

已有项目普通修改默认沿用现有技术栈；新项目、明确迁移或现有方案无法满足需求时再重新选型。

## 前端

Web 与桌面 GUI 使用同一套前端技术栈。

| 层 | 默认选择 |
|---|---|
| Framework | React + TypeScript |
| Build | Vite |
| Components | Shadcn UI |
| Primitives | Base UI |
| Styling | Tailwind CSS |
| Icons | Lucide |

组件库、样式技术属于技术选型；具体视觉风格、颜色、间距、圆角、布局和交互规范由 `ui-style` 负责。

## 后端

### 语言

| 用途 | 默认选择 | 使用条件 |
|---|---|---|
| 主后端 / 业务主体 | Go | 默认选择 |
| 极限性能模块 | Rust | 明确存在 CPU、延迟、吞吐或内存方面的高性能需求 |
| 生态型模块 | Python | 第三方库或生态明显更强，例如 asyncua、pandas、scipy 等 |

整体优先保持 **Go 主体 + 按需 Rust / Python 模块**，不因为局部需求切换整个后端技术栈。

### 桌面宿主

前端技术栈不因桌面宿主变化而改变。

| 场景 | 选择 |
|---|---|
| 应用主体以 Go、本地系统能力和业务逻辑为主 | Wails + Go |
| 明显依赖 Node.js / npm / Bun 生态、插件系统、Code Agent / CLI / SDK 集成 | Electron + Node.js |

Wails 与 Electron 是平级桌面路线，按宿主能力选择，不预设其中一个永远优先。

### 数据库与中间件

数据库按**数据模型、数据规模、读写模式、并发和性能需求**选择，不预设固定数据库。

Redis、消息队列、搜索引擎、对象存储等中间件只有出现明确需求时再引入，不为未来假设提前增加部署复杂度。

### 部署约束

当前目标环境以**打包后直接运行在 Windows / Linux** 为主。

- Go / Rust 产物分别构建对应平台版本；
- Python 模块正式分发时必须处理运行时和依赖，不能假设目标机器已安装开发环境；
- 默认避免必须额外部署和维护独立服务的基础设施，除非需求明确值得增加复杂度。

## 默认不要提前引入

**微服务 · Kubernetes · 消息队列 · Redis · 第二种主后端语言 · Python Worker · Rust 模块 · 独立中间件服务 · 多层架构模板**

只有当前需求已经产生明确收益时才引入，不为未来假设提前设计。

## 输出

只输出：**选择：** `<技术路线>`　**原因：** `<2~4 个关键原因>`　**偏离默认：** `<有则写，没有省略>`

只有两个方案会造成明显不同的产品结果、且需求无法判断时，才让用户选择；普通技术细节由 Agent 直接决定。
