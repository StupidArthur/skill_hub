# 技术选型

本 Skill 只负责**做技术决策**，不维护框架教程、固定版本、代码模板或目录脚手架。

## 核心原则

1. **已有项目优先**：除非任务就是迁移或现有方案存在实质问题，否则沿用已有语言、框架、组件体系和部署方式。
2. **需求驱动，不追新**：选择能最简单可靠满足需求的成熟方案，不因为新颖或个人偏好增加技术复杂度。
3. **减少运行时和技术栈数量**：能单栈解决就不引入第二语言、第二服务或额外进程。
4. **Agent 负责推荐**：常规 Go/Python/JS、框架和库选择由 Agent 基于上下文判断，不把普通选型题直接甩给用户。
5. **只记录关键取舍**：说明最终选择和主要原因即可，不输出百科式对比报告。

## 选型流程

### ① 判断是否真的需要重新选型

- 已有项目的普通功能修改：通常不重新选型。
- 新项目、架构迁移、核心依赖替换、部署模式变化：进入选型。

**完成标志**：确认本次是否存在真实的技术决策。

### ② 识别约束

按实际任务关注：

- 产品形态：桌面 GUI、Web、CLI、服务、批处理、库；
- 部署与分发：本地、服务器、容器、离线、单文件或安装包；
- 生态依赖：AI、数据、硬件、协议、专有 SDK；
- 性能与并发要求；
- 跨平台要求；
- 长期维护成本和团队已有能力；
- 用户明确指定或禁止的技术。

不要为了填表而补齐无关维度。

### ③ 选择最小可行技术路线

优先选择当前主流、维护活跃、生态成熟且与约束匹配的方案。

#### 桌面 GUI 默认偏好

全新桌面工具默认优先：

```text
前端 UI
  ↓
Wails Binding / Adapter
  ↓
Go 业务与控制层
  ↓
系统能力 / 文件 / 数据库 / 可选 Python Worker
```

- Wails + Go 负责应用生命周期、桌面集成和业务编排。
- 前端框架不在本 Skill 中锁定，选择当前稳定且适合项目的 TypeScript 方案。
- 小项目保持简单，复杂度增长后再按业务拆分。
- 只有 Python 在核心能力上有明显优势时才增加 Worker，例如成熟 AI/数据/科学计算生态、专有 SDK、模型驻留或高资源任务隔离。
- 如果 Go 能简单可靠完成任务，就保持纯 Go。

引入 Python Worker 时只守这些边界：Go 管理启动/退出/超时/取消/异常；前端不直接调用 Python；IPC 结构化可校验；正式分发不能默认用户已配置开发用 Python 环境。

#### Web / CLI / 服务

不固定 React、Vue、Next、Gin、FastAPI、Cobra、Typer 等框架。已有项目跟随现状；全新项目根据约束选择当前成熟方案。

### ④ 输出决策

选型结论保持简短：

```text
选择：<技术路线>
原因：<最重要的 2~4 个理由>
主要代价：<真正需要注意的成本或风险>
```

只有存在两个影响明显不同、且无法从需求判断的方向时才让用户决定。

## 不维护的内容

- 框架基础教程和 API 用法；
- 固定版本号；
- 固定目录模板；
- 代码片段和脚手架；
- 为了“标准架构”提前增加的分层。

这些由 Agent 结合项目代码、依赖和当前官方资料自行处理。
