# 需求理解与项目勘察

> 流程阶段①。目标不是写一份完整需求文档，而是获得足够上下文后再动代码。

## 1. 判断任务深度

按风险和影响面选择流程深度，不按形式机械走完整流程。

- **轻量**：局部 Bug、文案/配置、小范围逻辑调整、明确的小重构。
- **标准**：新增功能、跨多个文件/模块的修改、接口或数据结构变化。
- **高风险**：架构迁移、数据迁移、大范围删除、生产配置、兼容性破坏、安全敏感修改。

轻量任务可以快速推进；只有高风险或存在关键歧义时才要求额外确认。

## 2. 已有项目先勘察

在提出方案前，按任务需要读取：

- 相关目录和入口文件；
- 直接调用链和数据流；
- 项目已有的架构、命名、依赖和代码风格；
- 相关测试、构建脚本和 CI 配置；
- 当前 Git 状态，区分用户已有改动与本次任务。

不要为了“理解整个仓库”进行无边界扫描，只调查与当前需求相关的部分。

## 3. 明确边界

至少在内部确认：

- 用户真正要得到的结果；
- 哪些行为必须保持不变；
- 本次修改的影响范围；
- 如何判断修改成功。

如果这些信息能从用户描述和项目代码可靠推断，就直接继续；不要为了流程完整而反问。

## 完成标志

能够用简短语言说明“现状是什么、准备改什么、如何验证”，即可进入 [设计阶段](design.md)。
