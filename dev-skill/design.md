# 方案设计

> 流程阶段②。设计只做到“足以安全实现”的程度，不追求文档完整度。

## 设计原则

- **已有项目优先沿用现状**：除非用户要求迁移或现有方案确有问题，不因为个人偏好更换框架、目录结构或架构模式。
- **最小设计**：能用局部修改解决的问题，不升级成系统性重构。
- **复杂度随风险增长**：轻量任务允许直接形成实现思路；复杂任务再补模块边界、数据流和迁移方案。
- **不要把选型问题甩给用户**：能根据需求和现有项目做出合理判断时直接推荐并说明原因；只有取舍会显著影响产品时再询问。

## 设计时关注什么

按任务实际需要选择，不要求每项都写：

- 修改哪些模块及其职责；
- 接口、数据结构或持久化是否变化；
- 兼容性、迁移和回滚风险；
- 并发、超时、取消、资源清理等运行边界；
- 测试和验收方式。

### 长任务或数据处理

如果中途失败会造成明显损失，再考虑幂等、checkpoint、原子写入、恢复和取消；不要给普通短任务强行增加这套机制。

### LLM 功能

如果代码调用 LLM 做下游决策，至少明确输入/输出契约、结构化校验、失败处理和危险操作边界。是否拆成多个调用点由实际复杂度决定，不强制固定模式。

## 技术选型

- 已有项目：默认沿用现有技术栈。
- 全新项目：根据需求、生态、部署和维护成本选择当前合适的主流方案。
- 桌面 GUI：本仓库保留一套明确偏好，见 [GUI 路线](design/gui-tool/README.md)。
- Web / CLI：不在 Skill 中维护框架教程或固定版本；按任务与当前生态选择即可。

## 什么时候需要用户确认

只有以下情况需要在编码前等待确认：

- 存在两个以上明显不同且影响较大的产品/架构方向；
- 方案会扩大用户要求的范围；
- 涉及破坏兼容性、迁移数据或难以恢复的修改；
- 关键需求无法从上下文可靠判断。

普通实现细节和低风险技术决策由 Agent 自行完成。

## 完成标志

方案足以指导实现，关键风险和验证方式已经明确，即进入 [实现阶段](coding-standards.md)。
