# 验证原则

> 流程阶段④。目标是获得足够证据证明需求已满足，而不是追求固定测试流程。

## 验证策略

优先使用项目已经存在的测试、构建、lint、typecheck 和运行方式。根据改动风险选择最小但充分的验证集合。

- **轻量修改**：针对改动点运行最相关的测试或检查。
- **标准修改**：覆盖核心逻辑，并执行相关模块的构建/静态检查；需要时补集成测试。
- **高风险修改**：增加端到端、迁移、兼容性、失败恢复或目标环境验证。

## 测什么

至少验证：

1. 用户要求的主要路径确实工作；
2. 与本次修改直接相关的关键边界或失败路径没有明显回归；
3. 修改涉及的代码能够按项目方式构建或运行。

不要机械要求每个函数、Handler、Binding 或 CLI 参数都写单元测试。测试层级由失败风险决定。

## 测试纪律

- 测试应隔离真实用户数据和生产环境。
- 不通过吞异常、跳过关键断言或修改产品语义来“让测试变绿”。
- 测试失败先判断是实现错误、环境问题还是测试本身问题，再处理。
- 没有实际执行的测试不能声称“已通过”；无法执行时明确说明原因。
- 新增测试优先覆盖回归风险，而不是追求覆盖率数字本身。

## 验收

测试命令通过不等于需求完成。最终回到需求阶段确定的成功标准，确认真实行为符合预期。

## 完成标志

已有足够验证证据，并清楚知道哪些内容尚未验证后，进入 [交付阶段](delivery.md)。
