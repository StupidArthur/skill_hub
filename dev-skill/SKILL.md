# 开发工作流

本 Skill 只约束**工作方式、风险边界和完成标准**，不重复模型已经掌握的语言、框架和工具知识。

## 核心原则

1. **先读再改**：已有项目先检查相关代码、结构、约定、测试和当前 Git 状态，再提出方案。
2. **按风险决定流程深度**：小改动快速推进；架构变更、数据风险和不可逆操作才增加确认环节。
3. **尊重现有项目**：现有技术栈、目录、风格和依赖优先于默认偏好，除非用户明确要求迁移或现状存在实质问题。
4. **最小必要改动**：解决当前需求，不顺手扩大范围，不做与任务无关的重构。
5. **用结果验收**：测试和构建只是证据，最终要回到用户需求和验收目标。

## 流程

### ① 理解需求与勘察项目

读 [requirement.md](requirement.md)。

- 判断任务是轻量、标准还是高风险。
- 已有项目先定位相关实现、调用链、测试和约定。
- 需求明确且风险低时直接继续，不为流程本身要求用户确认。

**完成标志**：知道要改什么、边界在哪里、现有实现如何工作。

### ② 设计修改方案

读 [design.md](design.md)。

- 轻量任务只需形成简短修改思路。
- 标准任务说明关键改动、影响面和验证方式。
- 高风险或存在重要取舍时才输出详细方案并请求确认。
- 需要重新做技术选型时，调用 [tech-selection](../tech-selection/SKILL.md)。
- 涉及新界面或显著视觉调整时，调用 [ui-style](../ui-style/SKILL.md)。

**完成标志**：方案足以指导实现，没有未处理的关键风险或歧义。

### ③ 实现

读 [coding-standards.md](coding-standards.md)。

按现有项目习惯完成最小必要修改。只有遇到新的重大取舍、范围扩张或不可逆操作时暂停确认。

**完成标志**：实现与方案一致，无无关改动。

### ④ 验证

读 [testing.md](testing.md)。

选择与改动风险相匹配的验证方式，优先使用项目已有测试、构建和检查命令。

**完成标志**：有足够证据证明需求已满足，并明确未验证或仍有风险的部分。

### ⑤ 交付

读 [delivery.md](delivery.md)。

总结修改、验证结果和剩余风险。只有用户要求时才执行提交、打包、发布等额外交付动作。

**完成标志**：用户能清楚知道改了什么、如何验证、还有什么未解决。

## 必须确认的情况

普通编码不需要逐阶段审批。以下情况才暂停并向用户确认：

- 需求存在会显著改变实现方向的歧义；
- 需要扩大用户明确要求之外的范围；
- 存在明显的产品/架构取舍且无法从现有项目推断；
- 会删除用户数据、重要资产或进行难以恢复的大范围修改；
- 涉及生产环境、真实凭据、发布、迁移等高风险操作。

## Definition of Done

开发任务完成时应满足：

- 用户需求和验收目标已覆盖；
- 修改范围合理，没有夹带无关重构；
- 相关测试/构建/静态检查已按需要执行；
- 必要的现有文档或接口说明已同步；
- 未解决问题、未执行验证和残余风险已明确说明。
